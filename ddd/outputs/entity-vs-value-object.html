Entity vs. Value ObjectTwo answers to “are these the same thing?”

Every object in a domain model has to answer one question: does identity matter, or only the data? The answer sorts it into one of two buckets — and the bucket decides how you write equals(), whether it can mutate, and how you're allowed to store and compare it.

In the library app, a specific Book in the catalog needs tracking across time — someone can correct its title without it becoming a different book. Its ISBN, on the other hand, is just a 13-digit fact. Two ISBNs with the same digits aren't "different ISBNs that happen to match" — they're the same value.

Side by side

Entity

Book

Has a thread of identity that persists while its data changes. You track it, not its current snapshot.

  • Equality compares the ID field only
  • Fields are free to mutate over its lifetime
  • Lives on, gets updated, not replaced
class Book {
    private final BookId id;      // identity
    private String title;         // mutable
    private String author;        // mutable

    @Override
    public boolean equals(Object o) {
        if (!(o instanceof Book other))
            return false;
        return id.equals(other.id);
    }
}
Value Object

ISBN

Has no identity of its own — it is its data. Interchangeable with any other instance holding the same value.

  • Equality compares every field
  • Immutable — never edited, only replaced
  • Discarded and recreated freely
record ISBN(String value) {
    ISBN {
        if (value == null
            || !value.matches("\\d{13}"))
            throw new IllegalArgumentException(
                "Invalid ISBN: " + value);
    }
}

A Java record isn't a coincidence here — records give you field-based equals()/hashCode() and immutability for free, which is exactly the contract a Value Object needs. It's the natural encoding for one, in modern Java.

The full comparison

EntityValue Object
Equality By identity (ID field) By all field values
Mutability Mutable — state changes in place Immutable — replaced, never edited
Lifecycle Tracked continuously over time Created and discarded freely
Java shape Class with an ID field, identity-based equals() Record, or immutable class with value-based equality
Copies Two copies with equal fields are still distinct Two copies with equal fields are the same value

Elsewhere in the library domain

Entities — Book, Member, Loan
Value Objects — ISBN, LoanPeriod, Money, Address

Deciding which one

  1. If two instances hold identical data, must the system still be able to tell them apart? → Entity. A Loan from Tuesday and an otherwise-identical Loan from Wednesday are not the same loan.
  2. If not — if "same data" simply means "same thing" — → Value Object. There's no meaningful sense in which two ISBN("978...")s are "different."
  3. Still unsure? Ask whether the object needs to be looked up or fetched again later by some reference. If yes, it needs identity — it's an Entity.
Common mistake

Giving a Value Object its own id field "just in case." If you find yourself adding an ID to ISBN or LoanPeriod, that's a signal you're forcing entity-shaped machinery onto something that only ever needed to be compared by value — it adds a layer of identity-tracking the domain never asked for.
