Aggregate RootThe boundary that owns consistency

A Book and an Isbn tell you what things are. An Aggregate tells you what things must stay true together — and who's responsible for enforcing that.

A cluster of Entities and Value Objects that must change as one consistent unit is an Aggregate. Exactly one Entity in that cluster — the Aggregate Root — is the only door in. Nothing outside reaches past the root to edit an inner object directly; every change is a method call on the root, and the root is where the invariant actually gets checked.

The root is the only entry point  ·  inner Value Objects are only reachable through it  ·  Book and Member are separate aggregates — Loan holds only their IDs, never the objects themselves.

The invariant lives on the root

Outside code never touches LoanPeriod or flips the status directly. It calls a method on Loan, and Loan decides whether the request is even legal:

class Loan {
    private final LoanId id;
    private final BookId bookId;      // reference, not the Book itself
    private final MemberId memberId;  // same for the borrower
    private LoanPeriod period;
    private LoanStatus status;

    public void markReturned(LocalDate returnedOn) {
        if (status == LoanStatus.RETURNED)
            throw new IllegalStateException(
                "Loan " + id + " was already returned");
        this.status = LoanStatus.RETURNED;
    }
}

The rule "you can't return a loan twice" has exactly one legal home: inside the object that owns status. Put it in a service instead, and every new caller has to remember to re-check it — and eventually one won't.

What this forces you to do

  1. 01

    Reference other aggregates by ID only

    Loan holds a BookId, never a Book. If it held the object, editing one aggregate could ripple into another without either root getting a say.

  2. 02

    Repositories exist only for roots

    You'll write a BookRepository and a LoanRepository — never an IsbnRepository or a LoanPeriodRepository. Inner objects are only ever loaded as part of their root.

  3. 03

    One aggregate, one transaction

    Saving an aggregate is one unit of consistency — typically one database transaction. Needing two aggregates to change atomically together usually means the boundary is drawn in the wrong place.

  4. 04

    No public setters on inner objects

    Mutation is exposed as behavior on the root (markReturned(...)), not as raw field access. If it's settable from outside, the boundary has a hole in it.

Sizing the aggregates already in play

Book — its own root

Book doesn't need to change atomically with anything else. Small aggregate: just itself, with Isbn embedded as a Value Object.

Loan — a second, separate root

References Book and Member only by ID. Creating a loan never requires loading either of those aggregates fully into memory.

Common mistake

Making Book part of the Loan aggregate — or worse, one giant Library aggregate holding every book and loan in the system. The tell: if you can name a business rule that spans two objects but doesn't actually need to be enforced atomically, they're probably separate aggregates that should reference each other by ID instead.
