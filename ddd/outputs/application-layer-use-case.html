Application LayerWhere the outside world meets the domain

Everything built so far — Book, Loan, Member — lives in the Domain Layer and knows nothing about who calls it or why. A Use Case is the layer just outside that: one specific action someone wants to perform, and the script that carries it out.

A Use Case is a script, not a rulebook

Its job: load the aggregate(s) via a repository, call behavior methods on them, save the result. If you find an if deciding whether something is valid inside a Use Case, that rule usually escaped from where it belongs.

Leaks the rule
if (member.getStatus()
        == MembershipStatus.SUSPENDED) {
    throw new IllegalStateException(
        "Member cannot borrow");
}
Asks the aggregate
if (!member.canBorrow()) {
    throw new IllegalStateException(
        "Member cannot borrow");
}

Same outcome, different owner. On the right, what it means to be allowed to borrow stays on Member — reusable everywhere, testable without a Use Case at all, exactly like you already proved when you wrote canBorrow().

Repositories are Ports

A Use Case depends on an interface defined in the domain — never a concrete database. That interface is a Port; a real implementation (JPA, in-memory, whatever) is an Adapter that satisfies it later.

public interface BookRepository {
    Optional<Book> findById(BookId id);
    void save(Book book);
}

This is what makes the testing question interesting: a test hands the Use Case an in-memory, Map-backed fake implementing the same interface. The Use Case cannot tell the difference — it only ever depended on the interface, never on how storage actually works.

Worked example — BorrowBookUseCase

public class BorrowBookUseCase {
    private final BookRepository books;
    private final MemberRepository members;
    private final LoanRepository loans;

    public BorrowBookUseCase(BookRepository books,
            MemberRepository members, LoanRepository loans) {
        this.books = books;
        this.members = members;
        this.loans = loans;
    }

    public LoanId handle(BookId bookId, MemberId memberId) {
        Book book = books.findById(bookId)
            .orElseThrow(() -> new IllegalArgumentException("Book not found"));
        Member member = members.findById(memberId)
            .orElseThrow(() -> new IllegalArgumentException("Member not found"));

        if (!member.canBorrow())
            throw new IllegalStateException("Member cannot borrow right now");
        if (loans.hasActiveLoanForBook(bookId))
            throw new IllegalStateException("Book is already on loan");

        Loan loan = new Loan(LoanId.generate(), bookId, memberId,
            new LoanPeriod(LocalDate.now(), LocalDate.now().plusWeeks(2)));

        loans.save(loan);
        return loan.getId();
    }
}

What belongs where

  • USE CASEFetching aggregates via a repository

    Loading is orchestration — it has to happen somewhere outside the aggregate, since an aggregate can't load itself.

  • USE CASECalling behavior methods and saving the result

    member.canBorrow(), constructing the new Loan, loans.save(loan) — all orchestration, no decisions of its own.

  • AGGREGATEDeciding whether an action is valid

    "Can this member borrow" is a business rule. It belongs on Member, not re-implemented as an if in every Use Case that needs the answer.

  • AGGREGATEMutating fields directly

    A Use Case should never do loan.status = RETURNED — that's exactly the raw-setter problem Aggregate Root exists to prevent, regardless of which layer is doing it.

The interesting exception — rules that span aggregates

loans.hasActiveLoanForBook(bookId) can't live inside Book — Book doesn't know Loan exists, by design. "Is this book available" is a real domain rule, but an inherently cross-aggregate one, so the Use Case (or, once reused across multiple Use Cases, a Domain Service) is its correct home — not a fallback for a rule that couldn't find a "proper" place.
